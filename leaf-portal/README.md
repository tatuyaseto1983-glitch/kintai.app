# 株式会社リーフ 社内ポータル 勤怠管理（GASバックエンド）

Google スプレッドシートをデータベースにして、Google Apps Script（GAS）で勤怠を処理するバックエンドです。
**スタッフ画面（K）と管理者画面（L）** も入っています（同じWebアプリの中で切り替え）。

> このフォルダは、リポジトリ直下の `gas/`（ID・パスワード方式の別の勤怠アプリ）とは**別物**です。
> 混ぜずに、**新しいスプレッドシート**に入れてください。

## B. 最初にやる作業（clasp でパソコンから一括反映）

ファイルを1つずつコピーする代わりに、Google 公式のツール **clasp（クラスプ）** を使って、
パソコンの `leaf-portal/gas` にある24ファイルをまとめて Apps Script に反映します。

### 全体の流れ

```
[1] 新しいスプレッドシートを作る → [2] Apps Script を開いてスクリプトIDをコピー
→ [3] Apps Script API をオン → [4] パソコンの準備（Node.js・ファイル）
→ [5] clasp login → [6] .clasp.json にスクリプトIDを書く → [7] npm run push
→ [8] setupSystem を実行 → [9] runAllScenarioTests を実行
```

> **安全のための約束**
> - 反映先は **この勤怠システム用に新しく作ったスプレッドシートの Apps Script だけ**にしてください。
>   既存の勤怠アプリ（リポジトリの `gas/`）の Apps Script を指定すると、そちらのコードが置き換わって動かなくなります。
> - `clasp push` が置き換えるのは **Apps Script のコードだけ**です。スプレッドシートのデータ（シートの中身）は変わりません。
> - コードの修正は **パソコン側だけ**で行い、`npm run push` で反映します。
>   ブラウザの Apps Script 画面で直接書き換えると、次の push で上書きされて消えます。`clasp pull` は使わないでください。

### B-1. 新しいスプレッドシートを作る

1. ブラウザで Google ドライブを開き、**新規 → Google スプレッドシート → 空白のスプレッドシート**
2. 左上の「無題のスプレッドシート」を「**リーフ 勤怠データ**」などに変更

### B-2. Apps Script を開いて「スクリプトID」をコピーする

1. そのスプレッドシートのメニュー **拡張機能 → Apps Script** を開く（スプレッドシートに紐づいたプロジェクトが作られます）
2. 左上の「無題のプロジェクト」を「**リーフ 勤怠システム**」などに変更
3. 左端の **⚙（プロジェクトの設定）** を開く
4. 「ID」の **スクリプト ID** の横の「コピー」を押す（`1` で始まる50文字以上の英数字）
   - ※「デプロイID（AKfy… で始まる）」や、スプレッドシートのURLの中のIDではありません
5. このタブは開いたままにしておく

### B-3. Apps Script API をオンにする（最初の1回だけ）

1. ブラウザで **https://script.google.com/home/usersettings** を開く
   （スプレッドシートと同じ Google アカウントでログインしていること）
2. 「**Google Apps Script API**」を **オン** にする
3. オンにしてから反映まで数分かかることがあります

### B-4. パソコンの準備

1. **Node.js をインストール**：https://nodejs.org/ja から「**LTS（推奨版）**」をダウンロードしてインストール（20 以上が必要）
2. **コマンドを打つ画面を開く**
   - Windows：スタートメニューで「**コマンドプロンプト**」を開く（PowerShell より問題が起きにくいです）
   - Mac：「アプリケーション → ユーティリティ → **ターミナル**」
3. Node.js が入ったか確認（`v20` 以上の数字が出れば OK）
   ```
   node -v
   ```
4. **このリポジトリのファイルをパソコンに置く**
   - GitHub でリポジトリを開き、ブランチを `claude/festive-cori-wqhu6m` に切り替え →
     緑の **Code → Download ZIP** → ダウンロードした ZIP を右クリックで「すべて展開」
   - （git を使える方は `git clone` でも構いません）
5. **leaf-portal フォルダに移動**：`cd ` と入力（cd の後ろに半角スペース）してから、
   展開したフォルダの中の **leaf-portal フォルダを画面にドラッグ＆ドロップ** → Enter
   ```
   cd （leaf-portal フォルダの場所）
   ```
6. clasp をインストール（このフォルダの中だけに入ります。1〜2分）
   ```
   npm install
   ```

### B-5. clasp にログインする（最初の1回だけ）

```
npm run login
```

1. ブラウザが開くので、**スプレッドシートを作ったのと同じ Google アカウント**を選ぶ
2. 「Google hasn't verified this app」などが出たら内容を確認して続行し、権限の一覧は **すべて許可**（「すべて選択」があれば選ぶ）
3. ブラウザに「Logged in! You may close this page.」と出たら成功。コマンド画面に戻る
4. 確認：`npm run whoami` で自分のメールアドレスが出れば OK

ログイン情報はパソコンのユーザーフォルダの `.clasprc.json` に保存されます（このフォルダには入りません。人に渡さないでください）。

### B-6. `.clasp.json`（反映先の設定）を作る

`.clasp.json` は「どの Apps Script に反映するか」を書く小さなファイルです。見本の `.clasp.json.example` をコピーして作ります。

Windows（コマンドプロンプト）：
```
copy .clasp.json.example .clasp.json
notepad .clasp.json
```
Mac（ターミナル）：
```
cp .clasp.json.example .clasp.json
open -e .clasp.json
```

開いたファイルの `ここにスクリプトIDを貼り付け` を、B-2 でコピーしたスクリプトIDに置き換えて保存します。

```json
{
  "scriptId": "1AbC...（B-2 でコピーしたID）...xyz",
  "rootDir": "gas"
}
```

- `"rootDir": "gas"` は「leaf-portal/gas の中のファイルだけを反映する」という意味です。変えないでください。
- `.clasp.json` は人・環境ごとに違うため、Git には保存されません（`.gitignore` 済み）。

設定の確認（反映はしません）：
```
npm run check
```
`✔ 反映先のスクリプトID：…` と `✔ 反映するファイル（32個）` が出れば OK。
表示されたIDが、Apps Script の ⚙ に出ている「スクリプト ID」と同じか見比べてください。

### B-7. 全ファイルを反映する（`clasp push`）

```
npm run push
```

- 最初に自動で設定を確認し、問題があれば ✖ を表示して **反映せずに止まります**
- 「Manifest file has been updated. Do you want to push and overwrite?」と聞かれたら `y` → Enter
  （`appsscript.json`＝日本時間などの設定を反映してよいか、という確認です）
- `Pushed 31 files at （時刻）.` と出れば成功
- Apps Script のタブを **再読み込み** すると、左に `Config.gs` など31ファイルが並びます
  （最初からあった `コード.gs` は、パソコン側にないので消えます。これで正常です）

コードを直したときも、同じく `npm run push` だけで反映できます。

### B-8. `setupSystem()` を実行する（シートの作成）

1. Apps Script の画面で、左の一覧から **`Setup.gs`** をクリック
   （上の「実行する関数」の一覧には、**開いているファイルの関数**が出ます）
2. 上の一覧から **`setupSystem`** を選び、**▷ 実行**
3. 初回は「承認が必要です」→ **権限を確認** → ご自身のアカウント →
   「このアプリは Google で確認されていません」→ **詳細** → **（プロジェクト名）（安全ではないページ）に移動** → **許可**
4. 下の「実行ログ」に **【セットアップ結果】** と11シートの結果が出れば成功
5. スプレッドシートのタブに戻り、11のシートができているか確認
   `スタッフマスタ / 勤怠記録 / 中断履歴 / 打刻修正申請 / 残業申請 / 日報 / 設定 / 日報_接客 / 日報_確認 / 日報_コメント / 日報_更新履歴`
6. スプレッドシートを再読み込みすると、上のメニューに **「勤怠システム」** が出ます

- `setupSystem()` は **何回実行しても安全**です。既存のシート・データ・設定値は消しません。
  足りないシート、足りない見出し（右端に追加）、足りない設定項目だけを追加します。
- 最初からある「シート1」は削除しません。不要なら手で削除してください。

### B-9. `runAllScenarioTests()` を実行する（実機での自動テスト）

1. 左の一覧から **`TestRunner.gs`** をクリック
2. 上の一覧から **`runAllScenarioTests`** を選び、**▷ 実行**（1〜3分かかります）
3. 実行ログの最後に **「◯件中◯件 成功（すべて成功）」** と出れば OK
4. マイドライブに「**Leaf勤怠_自動テスト用（削除してOK）**」というファイルができます。
   テストはこの別ファイルの中だけで行うので、**本番のスプレッドシートには書き込みません**

あわせて **`testLoginCheck`**（同じ `TestRunner.gs`）を実行すると、
あなたのメールアドレスが取得できているか・スタッフマスタに登録されているかを確認できます（データは変えません）。

### （予備）clasp を使えないとき

Apps Script 画面の左の **＋ → スクリプト** でファイルを作り、`leaf-portal/gas` の各 `.gs` の中身を貼り付けても動きます
（ファイル名は `.gs` を除いた名前。作る順番は自由）。`appsscript.json` は ⚙ で「"appsscript.json" マニフェスト ファイルをエディタで表示する」をオンにすると編集できます。

## E. 画面から呼ぶ関数（`google.script.run` で呼びます。スタッフ画面で使っているものは K-1）

戻り値はすべて同じ形です。

```js
{ success: true,  message: '出勤しました（出社・09:30）', data: { ... } }
{ success: false, message: '本日はすでに出勤済みです（出勤 09:30）', data: null }
```

| 関数 | 誰が | data の中身 |
|---|---|---|
| `getCurrentUser()` | 全員 | employeeId, name, email, role, isAdmin, workType, department |
| `clockIn('出社' または '在宅')` | 全員 | 勤怠1件（下の「勤怠の項目」） |
| `startBreak(理由)` / `resumeWork()` / `clockOut()` | 全員 | 勤怠1件 |

## F. 【重要】ログインユーザー判定：Google Workspace 運用と個人 Gmail 運用の違い

このシステムは `Session.getActiveUser().getEmail()`（操作している人のメールアドレス）でスタッフを判定します。
**このメールアドレスが取れるかどうかは、アカウントの種類と Webアプリの公開設定で変わります。**

### いつ取れるか

| 使い方 | Google Workspace 運用（全員が @会社ドメイン） | 個人 Gmail 運用（全員が @gmail.com など） |
|---|---|---|
| Apps Script 画面から実行（今回のテスト） | 取れる | 取れる |
| スプレッドシートのメニューから実行 | 取れる | 取れる（その人に編集権限がある場合） |
| Webアプリ：「自分」として実行 | **取れる**（所有者と利用者が同じドメインの場合） | **取れない（空になる）** ※所有者本人だけは取れる |
| Webアプリ：「アクセスしているユーザー」として実行 | 取れる | 取れる。ただし全員にスプレッドシートの編集権限が必要 |

### 取れないときの動き（コードで保証していること）

- メールアドレスが空・取得時にエラー・形式がおかしい場合は、**必ずエラーで止まり、打刻などは一切記録しません**。
  画面には「Googleアカウントのメールアドレスを取得できませんでした。打刻などの処理は行っていません。…」と返します。
- `Session.getEffectiveUser()`（＝スクリプトを実行している権限の持ち主。「自分として実行」なら所有者）で
  **代用することはしません**。代用すると、全員が所有者として打刻される誤動作になるためです。
- 確認用に `testLoginCheck`（TestRunner.gs）を用意しています。取得できたアドレスと、スタッフマスタでの判定結果をログに出します。

### どちらで運用するか（画面を作る前に決める）

| | 内容 | 良い点 | 注意点 |
|---|---|---|---|
| **第一候補** | Google Workspace（会社ドメイン）で運用。Webアプリは「自分として実行」＋「アクセス：組織内のユーザー」 | 今のコードのまま使える。社外の人は開けない。スタッフにシートの権限を渡さなくてよい | Workspace の契約（有料）が必要 |
| 第二候補 | 個人 Gmail のまま。画面側で Google ログイン（Google Identity Services）を行い、GAS 側でログイン情報を検証してメールアドレスを確認する方式に変更 | 追加費用なし | 画面・GAS の追加開発が必要（次の段階で対応可） |
| おすすめしない | 個人 Gmail で「アクセスしているユーザーとして実行」＋全員にシートの編集権限 | すぐ動く | スタッフがシートを直接書き換えられ、「申請→承認」の仕組みが意味をなくす |

## G. データの保存形式と、シートを直接直すときの注意

- 日付・時刻・時間は **文字列（書式なしテキスト）** で保存しています（例：`2026-09-29`、`09:30`、`08:10`、`138:00`）。
  「09:30」が勝手に別の値に変わるのを防ぐためです。手で入力するときも同じ形で入力してください。
- 列は **見出し名** で探しているので、列の並べ替えや右側への独自の列の追加をしても動きます。**見出し名は変えないでください**。
- シート上で出勤・退勤・中断履歴・残業申請のステータスを直接直したら、
  メニュー **勤怠システム → 今月の勤怠を再計算（管理者）** で計算列（実働・社内超過・要確認など）を更新してください。
- 勤怠記録・申請の行は削除しないでください（修正は打刻修正申請で）。

## H. 勤怠ルール（実装内容）

- **実働時間** ＝ 退勤 − 出勤 − 自動休憩（1:00）− 中断合計（マイナスにはしない）
  - **中断と昼休みの使い分け（R-1・確定）**：［中断］は **私用外出・通院など、勤務から離れるとき** に押します。**昼休みは中断にしません**（昼休みは自動休憩として差し引きます）。
    中断と自動休憩は別々に差し引くため、昼休みに中断を押すと休憩が二重に引かれます。スタッフ画面の中断ボタンの下にも同じ説明を出しています。
    （将来、社労士の確認（W-6 の Q-7）を受けて「中断を休憩に充てる」「理由で区別する」に変える可能性はありますが、今は変えません）
- **固定勤務**：09:30 より後の出勤は「遅刻」、18:30 より前の退勤は「早退」、18:30 以降は「社内超過時間」（1分単位）
  - 社内超過時間は**社内管理用の数字**で、法律上の時間外労働（1日8時間・週40時間超）の計算とは別です
  - 30分以上なら承認済みの事前残業申請が必要。なければ「要確認」。**打刻・実働は申請に合わせて削ったり丸めたりしません**
- **フレックス**：遅刻・早退・社内超過は判定しません。週 32:00・月 138:00 に対する実働・残り・超過を集計
- **週1日の完全休日**：出勤記録がない日を完全休日として数え、`getFlexSummary()`（本人）と `checkWeeklyRestDays()`（管理者・全員）で確認
- **日付をまたぐ勤務**（例：22:00〜翌1:00）：前日の記録に退勤できます
- **同時実行**：出勤・退勤・中断・再開・申請・承認は LockService で1件ずつ順番に処理

### 設定シートの項目

指示いただいた10項目に加えて、次の3項目を追加しています（初期値は指示どおりの動きになる値です）。

| 項目 | 初期値 | 意味 |
|---|---|---|
| 週_起算曜日 | 月 | 週の集計を何曜日から始めるか |
| 月_締め日 | 末日 | 「末日」または 1〜27（例：20＝21日〜翌月20日） |
| 自動休憩_適用開始 | 00:00 | 中断を除いた勤務時間（退勤−出勤−中断合計）がこの時間を**超えた**日だけ自動休憩を引く（00:00＝常に引く） |

**短時間勤務で自動休憩を引かないようにするには**：「設定」シートの `自動休憩_適用開始` の値を `06:00` に変えるだけです（コードの修正は不要）。
次の退勤から、中断を除いて6時間ちょうどまでの日は自動休憩 00:00、6時間を超えた日は 01:00 になります。
すでに記録済みの日も直したいときは、メニュー「今月の勤怠を再計算（管理者）」を実行してください。
何時間にするか（例：法律上は6時間超で45分・8時間超で1時間の休憩が必要）は、社労士に確認のうえ決めてください。

## K. スタッフ画面（Webアプリ）

ブラウザ（PC・スマホ）から、出勤・中断・再開・退勤、今日の記録、今月の勤怠、フレックス累計、全スタッフの状況、

### K-2. 既存のバックエンドへの変更（理由と内容）

既存の関数の動き・既存の戻り値の項目は変えていません。変更は次の2点です。

- **`setupSystem()` `addSampleStaff()` `runAllScenarioTests()` の先頭に、「エディタ・メニューから本人として実行されているか」の確認を追加**（`Setup.gs` の `requireEditorExecution_`）
  - 理由：Webアプリとして公開すると、Apps Script の仕組み上、名前の最後に `_` が付いていない関数は、スタッフがブラウザの開発者ツールから呼び出せてしまいます。
    「自分として実行」で公開すると、これらが**所有者の権限で**動き、テスト用スタッフが本番シートに追加されたり、所有者のドライブにテスト用ファイルが作られたりするおそれがあるためです。
  - 動き：Webアプリ経由（操作している人 ≠ 所有者）のときは「Webアプリからは実行できません」で止まります。
    エディタから実行する場合は今までどおり動きます（自動テスト 43件もそのまま成功します）。
- **`getTodayStaffStatus()` の各行に `isSelf`（自分の行なら true）を追加**（`AttendanceService.gs`）
  - 理由：全スタッフ一覧の「（あなた）」を氏名で判定すると、同姓同名のときに2人とも「あなた」になるため。サーバー側で社員IDを比べて判定します
  - 既存の項目（name, workStyle, status, label）は変えていません。社員IDやメールアドレスは返しません
- 追加（変更ではない）：`WebApp.gs` の `doGet()` と `getStaffDashboard()`。

### K-4. まず自分だけで確認する（テストデプロイ）

公開前に、自分だけが開けるURLで動作を確認できます。

2. Apps Script の画面右上の **デプロイ → デプロイをテスト**
3. 「種類の選択」の歯車 ⚙ で **ウェブアプリ** が選ばれていることを確認

- 自分のメールアドレスがスタッフマスタに登録されている必要があります（D の手順）。

### K-5. スタッフに公開する（新しいデプロイ）

会社の Google Workspace アカウントでの運用を前提にしています（理由は F）。

1. Apps Script を開く（スプレッドシートの **拡張機能 → Apps Script**、またはパソコンで `npm run open`）
2. 右上の **デプロイ** を押す
3. **新しいデプロイ** を選ぶ
4. 「種類の選択」の歯車 ⚙ → **ウェブアプリ**
5. 説明：例「スタッフ画面 v1」
6. **次のユーザーとして実行**：**自分（あなたのメールアドレス）** を選ぶ
   - スタッフはスプレッドシートの権限がなくても、この画面からだけ打刻できます

## L. 管理者画面

スタッフ画面と同じWebアプリの中にあります。スタッフマスタの権限が `admin` の人だけ、ヘッダーに **「管理者画面」** ボタンが出ます。
URL の最後に `?view=admin` を付けて開くこともできます（例：`…/dev?view=admin`）。

### L-1. 安全の仕組み

- 管理者画面のデータは、`getAdminDashboard()` がサーバー側で **`requireAdmin()` を通った場合だけ** 返します。
  ボタンが見えるかどうか（画面の表示）には頼っていません
- 一般スタッフが `?view=admin` で開いたり、ブラウザの開発者ツールから関数を直接呼んだりしても、
  **「管理者権限がありません」** と表示され、データは1件も返りません（自動テストで確認済み）
- 承認・却下・CSV・再計算も、それぞれの関数の中で `requireAdmin()` を実行します

### L-2. 画面の内容

## M. 残業申請フォーム（スタッフ画面）

固定勤務の人のスタッフ画面に **「残業申請」** カードがあります（フレックス勤務の人には表示しません）。

### M-1. ルール

基準の時間は **設定シートの「残業_申請不要上限」**（初期値 `00:30`）です。画面の説明文・自動判定・エラーメッセージもすべてこの値を使います
（例：`00:45` にすると「45分未満の残業は事前申請不要です」）。保存してよいかの最終判定は、必ずサーバー側で設定シートの値を使って行います。

| 予定残業時間（予定終了 − 予定開始） | 扱い |
|---|---|
| 上限未満（初期値なら30分未満） | 「◯分未満の残業は事前申請不要です」と表示し、**申請できません**（保存しない） |
| 上限ちょうど・それ以上 | 申請できる（ステータス＝承認待ち） |

- 対象日は今日以降だけ（過去日は事前申請にならないため不可）
- 予定終了は予定開始より後の時刻（日付をまたぐ残業は、この画面からは申請できません。管理者に相談）
- 同じ日に「承認待ち」「承認済み」の申請があると、もう一度は申請できません（却下された日は再申請できます）
- 社員ID・氏名は画面から送らず、サーバーがログイン中のアカウントから入れます
- 退勤したとき：社内超過が30分以上で **承認済み** の申請があれば「要確認」は付きません。**承認待ち・却下は承認済み扱いにしません**
- 実績（社内超過）は、残業申請の「実績残業」に予定とは別に入ります。予定に合わせて丸めることはしません

### M-2. 既存コードの変更（理由）

- `submitOvertimeRequest()` のチェックを3つ追加（`OvertimeService.gs`）
  - フレックス勤務の人は対象外（固定勤務の18:30基準のルールを当てはめないため）
  - 予定終了が予定開始以前ならエラー（以前は日付をまたぐとみなしていた）
  - 予定が設定「残業_申請不要上限」未満ならエラー（リーフのルールで申請不要のため。メッセージの「◯分」も設定値から作る）
- `getStaffDashboard()` に `overtimeRule`（設定「残業_申請不要上限」の値。固定勤務の人だけ）を追加。画面はこの値で説明文と事前チェックを表示
  - 過去日・理由なし・二重申請・同時実行のロックは、既存のチェックをそのまま使っています
- `getStaffDashboard()` に `overtime`（自分の残業申請。固定勤務の人だけ）を追加
- 管理者画面：サマリーの表示名を「今月の打刻漏れ」「今月の残業要確認」に変更、
  週1日完全休日は「不足が確定した人」だけを警告にし、週の途中の「未確定」は軽い表示に分けた（判定の仕組み `checkWeeklyRest_` は変更なし）

### M-3. Google実機での確認手順

1. **最新のZIP** をダウンロードして展開：
   https://github.com/tatuyaseto1983-glitch/kintai.app/archive/refs/heads/claude/festive-cori-wqhu6m.zip
2. **`.clasp.json` をコピー**：前のフォルダの `leaf-portal/.clasp.json` を、新しい `leaf-portal` に入れる
   （名前が「.」で始まるので、見えないときは隠しファイルを表示する設定にしてください）
3. 新しい `leaf-portal` に移動して **`npm install`**
4. **`npm run check`** →「反映するファイル（31個）」と、いつものスクリプトIDが出ることを確認
5. **`npm run push`**（「overwrite?」には `y`）
6. Apps Script の画面を **再読み込み**
7. `TestRunner.gs` を開いて **`runAllScenarioTests`** を実行 →「43件中43件 成功」
8. **デプロイ → デプロイをテスト** → `/dev` の URL を開く（固定勤務のスタッフとして登録されたアカウントで）
9. **残業申請**：「残業申請」カードの「申請する」→ 対象日＝今日、予定開始 18:30、予定終了 19:15 →
   予定残業時間が「00:45」と出ることを確認 → 理由を入れて「申請する」→ カードに **承認待ち（オレンジ）**
   - ついでに予定終了を 18:50 にすると「30分未満の残業は事前申請不要です」と出て申請できないことも確認できます
10. **管理者画面で承認**：管理者アカウントで `/dev?view=admin` →「残業申請」の「承認」→ 確認画面で「承認する」

## N. 会社名・ロゴ（ヘッダー・タイトル・favicon）

| 表示する場所 | 内容 | 設定している場所 |
|---|---|---|
| ヘッダー左（スタッフ画面・管理者画面で共通） | 会社ロゴ ＋「Leaf Co.,Ltd.」＋「勤怠管理」（管理者画面は「勤怠管理｜管理者画面」） | ロゴ：`assets/logo.png`／会社名：`WebApp.gs` の `APP_BRAND_NAME` |
| ブラウザのタブのタイトル | Leaf Co.,Ltd.｜勤怠管理 | `WebApp.gs` の `WEB_APP_TITLE`（`APP_BRAND_NAME` ＋「｜勤怠管理」） |
| 画面の一番下 | Leaf Co.,Ltd. | `APP_BRAND_NAME` |
| ブラウザのタブのアイコン（favicon） | 今は Google の標準アイコン（下を参照） | `WebApp.gs` の `APP_FAVICON_URL` |

### ロゴを差し替えるとき

1. `leaf-portal/assets/logo.png` を新しいロゴ画像（PNG・200KB以下）に置き換える（ファイル名は同じ `logo.png`）
2. `leaf-portal` で `npm run logo` →「✔ ロゴを変換しました」
3. `npm run push`

Apps Script の Webアプリは画像ファイルをそのまま配信できないため、画像を文字（data URI）にした `gas/Logo.html` を一緒に反映しています。
画面はこの1か所だけを見てロゴを表示します。`Logo.html` が壊れていても、画面は会社名の文字だけで表示されます。

### favicon（タブのアイコン）について

Apps Script の Webアプリは、外側の Google の画面の中に表示されるため、HTML の中にアイコンを書いても効きません。
favicon を変えられるのは `setFaviconUrl()` だけで、**インターネットから見られる画像のURL（https://…）** が必要です（埋め込み画像は使えません）。

設定する場合：
1. ロゴ画像を、誰でも見られる場所に置く（例：会社のホームページにアップロード）
2. そのURLを `WebApp.gs` の `APP_FAVICON_URL = 'https://…/logo.png';` に入れる
3. `npm run push` → デプロイを新しいバージョンに更新

※ 小さなアイコン（16〜32px）では、横長のロゴは細い線がつぶれて見えにくくなります。正方形に切り抜いた画像（例：家のマーク部分）がおすすめです。

## P. 日報（全社員で共有）と、役員の勤怠集計からの除外

### P-1. 役員を勤怠の集計から外す（スタッフマスタ「勤怠集計対象」）

- スタッフマスタの右端に **「勤怠集計対象」** 列があります（`setupSystem()` で追加）。
- **「対象外」** にした人は、次の画面・集計に出ません：
  全スタッフ勤務状況、本日出勤・出勤中・退勤済みの人数、管理者画面の日別・月別・要確認・完全休日の確認、勤怠CSV。
- ログイン・日報の閲覧／確認／コメントは今まで通りできます。打刻もできます（集計に出ないだけ）。
- 空欄・「対象」は集計に入ります。氏名ではなくこの列で判定しています。

### P-2. 日報のしくみ

| 状態 | 見られる人 | できること |
|---|---|---|
| 下書き | **本人だけ**（管理者・役員にも返しません） | 何度でも保存・修正 |
| 提出済み | 在籍中の全社員 | 閲覧・「確認しました」・コメント |
| 旧日報（新しい仕組みより前に提出されたもの） | **本人と管理者だけ**（全社員には公開しない） | 閲覧のみ（修正・確認・コメントはできない） |

- 日付と担当者はサーバーが決めます（画面から送られた社員ID・氏名は使いません）。日付は「今日」。下書きを翌日に提出しても、作った日の日報のままです。
  段階4から、書き忘れた日（7日前まで・勤務実績あり）も本人が作れます（V章）。
- 「日報を提出」→ 確認ダイアログ →「提出する」で提出。本日の業務内容は提出時のみ必須。
- 提出後の修正は本人だけ。修正するとバージョンが1つ上がり、全員が「未確認」に戻り、一覧に「更新あり」が出ます。修正前の内容は「日報_更新履歴」に残ります。
- 「確認しました」の対象は **在籍中で「日報確認対象」が対象外でない社員から、提出者本人を除いた人**（役員も含められる。休職・退職は除く）。確認は「今のバージョン」に対してだけ数えます。
- コメントは任意。古い順に表示し、編集はできません。削除は管理者だけ（段階4。行は残します）。
- 入力された文字はすべて文字として表示します（HTMLとして解釈しません）。

### P-3. 追加したシート・列

| シート | 列 |
|---|---|
| 日報（既存・右端に追加） | 日報ステータス, バージョン, 接客件数, 課題・気づき, 申し送り内容, 管理者への相談・確認事項, 最終更新日時, 作成日時 |
| スタッフマスタ（既存・右端に追加） | 勤怠集計対象 |
| 日報_接客 | 接客ID, 日報ID, 社員ID, 並び順, 顧客名, 顧客名未確認, 来場のきっかけ, その他の内容, 接客内容, 対応結果, 補足コメント, 次回対応, 次回対応内容, 削除, 作成日時, 更新日時 |
| 日報_確認 | 確認ID, 日報ID, 日報バージョン, 社員ID, 確認者名, 確認日時 |
| 日報_コメント | コメントID, 日報ID, 社員ID, 社員名, コメント, 投稿日時 |
| 日報_更新履歴 | 履歴ID, 日報ID, バージョン, 操作, 社員ID, 社員名, 日時, 内容 |

既存の列名・シート名は変えていません。既存の日報（旧形式）は消さずに、本人と管理者だけに表示します（「課題・気づき」が空なら旧「課題・困りごと」を表示）。
旧日報かどうかは「日報ステータス」列が空かどうかで判断します。**この列を手で書き換えると、旧日報が全社員に公開されます**（書き換えないでください）。

### P-4. 反映後に1回だけやること

3. スタッフマスタの「勤怠集計対象」で、**光山（E001）・猪倉（E002）を「対象外」** にする

## R. 休日出勤申請

### R-1. しくみ

| 状態 | 次に進む操作 | 誰が |
|---|---|---|
| 申請中 | 承認 → 承認済み／却下（理由必須）→ 却下 | 管理者 |
| 申請中 | 取り下げ → **すぐ取消済み**（承認は不要） | 本人 |
| 承認済み | 取消申請（理由必須）→ 取消申請中 | 本人（休日出勤日が今日以降のとき） |
| 取消申請中 | 取消を承認 → 取消済み／取消を却下（理由必須）→ 承認済みに戻る | 管理者 |

## S. 勤務区間（段階1）：出社⇄在宅の切替・再出勤・20日締め

本番の基準点：タグ `prod-20261004-a08ec81`（コミット a08ec81、版 2026.10.02-5）。段階1で問題があれば、このタグのコードに戻せます。
段階1の版は **2026.10.04-3**（反映するファイルは 32個。`WorkSegmentService.gs` が増えます）。

### S-1. しくみ

- 1日の中で「出社 → 在宅」「在宅 → 出社」を切り替えたり、退勤後に再出勤したりすると、**勤務区間**が増えます。
  例：09:30〜16:00 出社 ＋ 18:00〜20:00 在宅 → 区間2つ。勤怠記録は 出勤 09:30／退勤 20:00／区間数 2。
- 勤怠記録はこれまでどおり **1日1行の合計** です。列の意味は変えていません。
  日次まとめは操作のたびに **すべての勤務区間から作り直します**：出勤＝全区間の最小の開始、退勤＝終了済みの区間の最大の終了（勤務中の区間があるときは空欄）、勤務形態＝最初に始まった区間。
  再出勤・切替・中断のあとでも、出勤（最初の開始）は変わりません。すでにある区間の開始時刻・勤務形態は、打刻の操作では書き換えません（同じ分の中の操作でも新しい区間を作り、0分の区間として残します）。
- 計算は時刻の重なりで行います（同じ中断を2回引かない）。
  - 区間の実働 = 区間の長さ − その区間と重なる中断。
  - 出社・在宅・現場外出の時間 = 勤務形態ごとの区間の実働の合計。
  - 自動休憩は **1日1回**（区間の実働の合計が「自動休憩_適用開始」を超えた日）。出社・在宅には振り分けません。
  - 実働 = 出社 ＋ 在宅 ＋ 現場外出 − 自動休憩。
  - 社内超過時間 = 18:30 より後に実際に働いた時間（**その時間帯の中断は除く**。法定の時間外労働とは別の社内管理の数字）。
  - 遅刻は最初の区間の開始、早退は最後の区間の終了で判定（固定勤務だけ。フレックスは判定しません）。
- 「12:00 に出社を中断 → 12:30 に在宅で再開」は、出社 〜12:00／在宅 12:30〜 になります。中断の30分は区間の外なので、実働から二重に引かれることはありません（中断合計には 00:30 と記録します）。

## Y. 再計算のプレビューと「設定変更後に未再計算」（版 2026.10.05-4）

### Y-0. きっかけ（本番で見つかった例）

2026/10/5 大森さん 出勤 04:57・退勤 08:18（3時間21分）が「自動休憩 01:00・実働 02:21」と表示された。
原因は計算の誤りではなく、**退勤した時点の設定「自動休憩_適用開始」が 00:00（以前の初期値）だった**こと。
自動休憩・実働は退勤（や修正・再計算）の時点の設定で計算して勤怠記録に保存し、画面・CSV は保存値を表示する。
あとで設定を 06:00 にしても、再計算するまで保存値は変わらない（過去の数字が勝手に変わらないための作り）。

### Y-1. 設定「自動休憩_適用開始_有効日」（新）

- この日付以降の勤務日に「自動休憩_適用開始」を使う。それより前の日は 00:00（常に差し引く＝以前の初期値）で計算する
- 空欄＝すべての日に「自動休憩_適用開始」を使う（これまでと同じ）。日付でない値は空欄と同じに扱い、プレビューで知らせる
- 決定事項：**自動休憩_適用開始＝06:00、有効日＝2026-09-21**（20日締めの 2026/09/21〜10/20 全体を同じルールで扱う）
- setupSystem で設定シートの末尾に空欄で追加される。値は手で入れる

### Y-2. 設定変更後に未再計算の印

- 退勤済みの勤怠記録について、保存値と「今の記録・設定で計算した結果」が違うと、管理者画面に **「設定変更後に未再計算」** を出す
  - 日別一覧の状態の列（変わる値も表示：例「自動休憩 01:00→00:00・実働 02:21→03:21」）
  - 上部のカード「設定変更後に未再計算 ◯件」（今の20日締め期間）
  - 社内詳細月次・要確認一覧（区分「再計算」）
- **表示する値は保存値のまま**（画面を開くたびに再計算して書き換えることはしない）
- 社労士確認用の詳細表（CSV）・社労士提出用Excel には印を入れず、未再計算の記録があれば完了メッセージで注意を出す

### Y-3. 再計算のプレビュー → 確認 → 再計算

   - プレビューのあとで記録・設定が変わっていたら、何も書き換えずに止まる（もう一度プレビュー）
